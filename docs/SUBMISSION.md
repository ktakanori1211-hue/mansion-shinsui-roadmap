■ 何を作ろうとしていましたか？
理事会の役員（電気の知識はない）が、住所 → 図面 → 止まるもの → A4 の順に迷わず進める4画面を作ろうとしていました。

■ Claude にどのように指示しましたか？
要件定義（WHY・WHAT）を docs に書き、画面ごとに「この画面で何を判断させるか」を伝えて実装させました。途中からは、電気の素人である家族に触ってもらった所感や、デザイナーの友人の助言をそのまま渡して直させました。

■ 何が起きましたか？期待していた結果と何が違いましたか？
指示を足すたびに画面にボタンと説明が積み上がり、画面3は操作ボタンが10個、A4 は文字が2,000字を超えて、何を判断する画面なのか分からなくなりました。住所を入れると「建物の検索」と「場所の判定」で2回待たされ、Web から見つけた建物名が図面を読むと消える、図面を読むと地下と推測される、といった画面同士の食い違いも起きました。期待していたのは「足すたびに前より分かりやすくなる」ことでしたが、逆でした。

■ どのように対処しましたか？
「足すなら同じだけ消す」「各画面の表面の文字数はテストで上限を見張る」を CLAUDE.md の決まりにして、Claude 自身に表面の文字数を数えるテスト（macOS の JavaScriptCore で画面の関数を呼ぶ）を書かせました。画面3は操作を「1 浸水シミュレーションを始める → 2 対策を切り替えて比べる → 3 図を切り替える」の3つに減らし、A4 は「今のまま／対策したら／本日決めること」の3つの数字を主役にして 1,200 字台に。住所の判定と建物の検索は1回の呼び出しにまとめ、図面は複数枚を同時に送って待ち時間を半分以下にしました。図面の階は「図面に表記があるときだけ使い、地下と推測しない」を読み取りの指示とサーバーの検証の両方に入れました。決定は毎回 docs/REQUIREMENTS.md に番号つきで残し（31回）、前の決定を Claude が勝手に戻さないようにしました。

## 11. 審査員用リンク・アクセス用ログイン情報など（text・任意）
